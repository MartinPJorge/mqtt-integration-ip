\section*{Pregunta Esencial}

\emph{¿Cómo podemos implementar un sistema completo de monitorización remota que permita al hospital RAID-BIO mejorar la atención y el bienestar de sus pacientes?}.

Los hospitales requieren sistemas de monitorización remota que permitan procesar y analizar en tiempo real los datos biométricos de los pacientes. Estos sistemas son complejos y están compuestos por diversos subsistemas: dispositivos IoT que registran los datos de los pacientes, redes de comunicación que los transmiten, sistemas de procesamiento y generación de alertas y herramientas de visualización de los datos y alertas.

Cada vez es más habitual que esta tecnología se integre en la red hospitalaria. Por ejemplo, en Valdebebas, un hospital está incorporando tecnologías para la monitorización remota de pacientes\footnote{https://cadenaser.com/cmadrid/2025/06/24/tecnologia-avanzada-y-humanizacion-de-la-hospitalizacion-asi-seran-las-habitaciones-del-hospital-blua-sanitas-valdebebas-radio-madrid/}
. En consecuencia, el mercado está demandando cada vez más profesionales especializados en estas tecnologías.

    \section*{Actividades guiadas}
A continuación se presentan las actividades mini-reto:


\begin{enumerate}[label=\textbf{Actividad {{\arabic*}}}]
    \item \textbf{Despliegue del escenario}: En primer lugar debe arrancar la máquina
virtual utilizada en el curso. Sírvase del comando de sesiones anteriores. Todas las indicaciones de ahora en adelante asumen que está dentro
de la máquina virtual.

Descargue los ficheros \texttt{install.sh} y \texttt{vnx-integracion.xml} que están disponibles en el Moodle de la asignatura. Por defecto se almancenarán en la carpeta \texttt{Downloads} de su máquina virtual. A continuación, abra una terminal y ejecute:
\begin{lstlisting}[language=bash]
$ cd ~/Downloads
$ sudo ./install.sh
\end{lstlisting}
en caso de que haya descargado los
ficheros en la carpeta
\texttt{\~{}/Downloads}.
Espere unos 5\,\textrm{min} para que
termine de desplegarse todo el escenario.

\item \textbf{Configuración de red.}  Configure las direcciones IP de las interfaces: 
h2.\texttt{eth1},
r1.\texttt{eth1},
r1.\texttt{eth2},
r2.\texttt{eth1},
r2.\texttt{eth2},
h3.\texttt{eth1}.
Para ello tiene que decidir qué prefijos
(por ejemplo \texttt{10.1.0.0/24})
tendrán las siguientes subredes:
\begin{itemize}
    \item Net0: compuesta por
        h2.\texttt{eth1} y
        r1.\texttt{eth1}.
    \item Net1: compuesta por
        r1.\texttt{eth2} y
        r2.\texttt{eth1}.
    \item Net2: compuesta por
        r2.\texttt{eth2} y
        h3.\texttt{eth1}.
\end{itemize}

Una vez haya definido los prefijos
de cada subred, decida qué direcciones
IP tendrá cada una de las interfaces que
hay en cada subred.
Para ello acceda a la consola del
dispositivo
(login: root, password: xxxx)
y ejecute:
\begin{lstlisting}[language=bash]
$ ip address add IP/PREF dev IF
\end{lstlisting}
donde \texttt{IP/PREF} es la dirección
a asignar a la interfaz \texttt{IF}
y \texttt{PREF} es la longitud del prefijo.

\emph{Nota}: la red Net3 interconecta
su host (la máquina virtual)
con el router virtual r1.
Esta red ya viene configurada, es decir, las interfaces eth3 de r1 y Net3-e00 del host ya tienen dirección IP.


\item \textbf{Configuración del reenvío IP}. En este apartado debe configurar las tablas de encaminamiento de los equipos \texttt{h2,h3,r1 y r2} para que haya conectividad entre todos los dispositivos del escenario. Para añadir una entrada en la tabla de encaminamiento de un nodo utilice el siguiente comando:



\begin{lstlisting}[language=bash]
$ ip route add SUBNET via NEXTHOP
\end{lstlisting}
Este comando especifica que para
llegar a la subred \texttt{SUBNET}
(por ejemplo, 10.1.0.0/24), hay que enviar el tráfico al siguiente salto \texttt{NEXTHOP} (por ejemplo, 10.1.0.2).

Cuando haya programado las tablas de encaminamiento de los nodos del escenario, haga pruebas con el comando \texttt{ping} para verificar la conectividad. 

\emph{Nota}: recuerde que el broker
EMQX se ejecuta como un contenedor
dentro de la máquina virtual.
El contenedor suele desplegarse en la
subred \texttt{172.17.0.0/16}.
Por tanto, deberá añadir rutas en todos
los equipos del escenario para poder
alcanzar el dicha subred.


\item \textbf{Arrancar broker EMQX, datasource y Grafana}. Para arrancar el servicio de detección de anomalías, primero debe
arrancar el contenedor del broker EMQX
y Grafana (junto al plugin del datasource).
Para ello, acceda al host (la máquina
virtual) y ejecute los comandos
ya utilizados en prácticas anteriores:
\begin{lstlisting}[language=bash]
$ docker run -d --name emqx -p 1883:1883 -p 8083:8083\
  -p 8883:8883 -p 8084:8084 -p 18083:18083\
  emqx/emqx:5.0.2

$ sudo docker run -d -p 3000:3000 --name=grafana \
  -e "GF_INSTALL_PLUGINS=grafana-mqtt-datasource" \
  grafana/grafana-enterprise
\end{lstlisting}
puede comprobar que todo se ha arrancado
correctamente si ve dos contenedores
al ejecutar
\begin{lstlisting}[language=bash]
$ docker ps
\end{lstlisting}

Para comprobar que h2 y h3 pueden
acceder al broker,
ejecute un \texttt{ping}
al broker EMQX.
Puede ver la dirección IP del broker
EMQX usando el siguiente comando:
\begin{lstlisting}[language=bash]
$ sudo docker inspect  \ 
  $(sudo docker ps | grep 5.0.2 | cut -d ' ' -f1) \ 
  | grep "IPAddress"
\end{lstlisting}

\item \textbf{Arrancar el cliente de MQTT}. Para arrancar este servicio, primero ejecute \texttt{client.py} (sirviéndose del \texttt{utils.py} y
        \texttt{reporter.sh}) en h2. Nota: deberá modificar la variable \texttt{broker} de su script. 

Si la conexión se establece con éxito podrá comprobar que el tráfico MQTT llega al docker que ejecuta el broker EMQX. Para hacer esta comprobación, ejecute en un terminal de la máquina virtual el comando:

\begin{lstlisting}[language=bash]
$ sudo docker exec -it emqx /bin/sh
\end{lstlisting}

Este comando le permitirá acceder a la consola del docker que ejecuta el broker. En la consola del docker, ejecute el siguiente comando: 

\begin{lstlisting}[language=bash]
$ emqx ctl log handlers set-level console debug
\end{lstlisting}

Este comando le permitirá configurar el fichero de log del broker. 

A continuación, en un terminal de la máquina virtual, ejecute el comando:

\begin{lstlisting}[language=bash]
$ sudo docker logs -f emqx
\end{lstlisting}

Este comando le mostrara los mensajes MQTT que está recibiendo el broker de MQTT.

\emph{Nota}: todos los archivos que tenga en la carpeta
\texttt{/home/upm/shared} de su máquina virtual están accesibles en la carpeta
\texttt{/shared} de los nodos del escenario (\texttt{h2,h3,r1,r2}). Cualquier cambio que haga en cualquiera de estos dos directorios se aplica en ambos. 

\item \textbf{Visualización de métricas}

En la máquina virtual, acceda a grafana y siga los pasos de prácticas anteriores
para visualizar cómo va evolucionando
la temperatura.


%Con el cliente MQTT ya conectado al broker, arranque el subscriptor \texttt{subs.py} en el h3.

\item \textbf{Arrancar el suscriptor/detector de anomalías}. Para finalizar, vamos a ejecutar el programa \texttt{subs.py} en la consola de h3. Recuerde que la dirección IP del broker debe corresponder con la del contenedor corriendo en el escenario. 

Si la configuración de red es correcta, debería recibir \texttt{PUBLISH}
desde el broker y ver en las capturas de wireshark las alertas que genera su detector de anomalías.

\end{enumerate}
